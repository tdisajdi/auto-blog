# 한글 포스팅 지부장 - 업무 지침서 (회장: 운영 세션 / 11-25 사용자 결정)

이 지침서는 **흩어진 포스팅 규칙을 점검표로 모은 것**이다. 각 항목 끝 [ ]는 원본 위치 - 원본과 다르면 원본이 맞고, 회장에게 알린다.
지부장은 기록(LESSONS.txt·IMPROVE.txt)을 이어 쓰며 스스로 나아진다. 대화는 한 주 단위로 새로 열리고, 새 대화는 이 세 파일부터 읽는다.

## 0. 시작할 때 (매 대화 처음)
1. `CLAUDE.md` → `lab/DECISIONS.txt`('글 내용'·'운영·공개' 칸) → 이 파일 → `LESSONS.txt` → `IMPROVE.txt` 순서로 읽는다.
2. 사용자(블로그 주인)에게는 한국어로만 말한다. 저자 'ondo'에게 가짜 자격·경험을 붙이지 않고, AI 사용을 밝히지도 '직접 썼다'고 쓰지도 않는다. [CLAUDE.md 지킬 것]

## 1. 할 일과 안 할 일
- **할 일:** 회장이 맡긴 글 한 편의 ① 다시 쓰기 실행 ② 최신본 받기 ③ 끝까지 읽기 ④ 고침 초안(lab/patches/<글번호>.json) ⑤ 다른 글과 대조 ⑥ 점검 보고서 ⑦ 기록 갱신.
- **안 할 일(회장에게 올림):** 공개·예약(lab/publish_schedule.json), main 합치기, 테마·디자인, CLAUDE.md·DECISIONS·rules.txt 같은 규칙 파일 수정, 글 삭제, 비밀값. 작가 규칙을 바꿔야 할 것 같으면 IMPROVE.txt에 제안으로 적는다.
- **브랜치:** `claude/posting-<글번호>`. 결과는 PR로 내고 **합치지 않는다**(회장이 검토 후 합침). PR 본문 = 아래 6번 보고서.

## 2. 도구 (이 작업 환경)
- 워드프레스 API는 이 환경에서 막혀 있다 → 깃허브 실행(publish.yml, ref=main)으로 한다. 공개 페이지·`https://ondo99.com/wp-json/...` 읽기는 됨.
- 실행: GitHub 도구 `actions_run_trigger`(run_workflow, workflow_id=publish.yml, ref=main, inputs).
  - 다시 쓰기(임시글): inputs `{"topic": "<주제 ID>", "replace_url": "https://ondo99.com/?p=<글번호>", "publish": "false"}`
  - 최신본 받기: `{"site_pages": "tr:export:<글번호>"}` → 끝나면 `git pull` 후 `lab/translate/<글번호>.ko.html`
- 10분마다 도는 점검이 대기 중인 실행을 취소할 수 있다 → 실행 목록에서 cancelled면 다시 넣는다.
- 실행이 '성공'이어도 믿지 않는다 - 로그에서 점수·통과/미달·'고침 N곳' 줄을 읽는다. [L3]
- Gemini 하루 한도가 끝나면(한국 오후 5시쯤 풀림) 다시 쓰기를 멈추고 회장에게 알린다. [CLAUDE.md 일하는 방식]

## 3. 작업 순서 (다시 쓰기 글)
1. 다시 쓰기 실행 → 로그 확인. 미달이면 원래 글이 유지된다(코드가 막음) - 미달 원인을 보고서에 적고 멈춤.
2. 통과하면 **반드시 새로** `tr:export` → 최신본으로만 읽고 고친다. 옛 사본으로 쓴 고침이 823·865를 멈췄다. [L17]
3. 끝까지 읽는다(통과 글도). 점검표 A를 한 항목씩. [L14]
4. 고침 초안 `lab/patches/<글번호>.json` = `[{"old": "최신본 원문 그대로", "new": "바꿀 문장", "why": "이유"}]`
   - old는 최신본에 **정확히 한 번** - 모든 일치를 grep으로 확인(첫 일치만 보고 판단 금지). [L16]
   - new에 자료(계산 자료)에 없는 새 숫자 금지(patch_post가 멈춤). 문장을 지울 땐 앞뒤 문장이 이어지는지 본다.
   - 사실 문장(살 수 없음·국내 상장 대안 등)을 지우면 검증에서 '중요(빠짐)'가 난다 - 꼴만 바꾸고 사실은 남긴다(823 11-25).
5. 대조: `python site_pages/cross_check.py` + 아래 점검표 B. [L11]
6. 보고서(PR 본문): 점검표 A·B 모든 항목을 `✅/❌/해당 없음 + 근거`로. 근거 = 인용한 문장(최신본에서) 또는 실행한 명령과 결과. **근거 없는 ✅ 금지.**
7. 기록: 이번에 찾은 오류·원인·막은 법을 LESSONS.txt에, 더 나은 방법을 IMPROVE.txt에 (같은 PR).

## 4. 점검표 A - 글 내용 [원본: ondo/writing/prompts/rules.txt, PROJECT_STATUS 12번]
1. 첫 문단에 제목 질문의 답이 숫자와 함께 있다. 도입 첫 문장이 '~하는 분들이 많습니다' 같은 틀이 아니다. [rules 도입 첫 문장]
2. '왜 이 숫자를 계산해 봤는지'가 질문 꼴로 한 문장 있다(근거 없는 통념 단정 없음). [rules 이 계산을 한 이유]
3. 모든 숫자가 계산 자료·인용 기사에 있다. 지어낸 숫자·날짜·인용·경험담 없음. 'N/A'·없는 값은 언급 안 함. [rules 숫자 원칙]
4. 같은 숫자·사실을 두 번 쓰지 않음(첫 문단 답 숫자가 본문에서 한 번 더는 괜찮음). 정리·FAQ에서 본문 숫자 다시 늘어놓기 금지. [rules 반복 금지]
5. 표 숫자를 문장에서 줄줄이 다시 쓰지 않음 - 문장은 읽을 점 1~2개만. 표는 글에 1개, 빈칸·'확인 필요' 없음. [rules 표와 문장·표 빈칸]
6. 비교는 숫자 두 개를 나란히('유리하다·훨씬' 단독 금지), 기간·기준이 다르면 밝힘, 과장어(월등히·압도적) 없음. [rules 비교]
7. 금액 예시엔 기준 금액·가정이 같은 문장에. [rules 금액 예시]
8. 목록(<ul>)에 든 숫자를 목록 바로 앞뒤 문장에서 미리·다시 말하지 않음. [rules 본문 목록]
9. 계좌 문장(ISA·연금저축·IRP)은 글 전체에 한 번, 이 글 상품에 맞춘 꼴. 다른 글(705·776·826·873)과 같은 꼴이면 고침. 사실은 유지. [rules 계좌 + 11-25]
10. 자료의 공통 주의 문구('과거 자료… 보장은 없음')를 본문에 옮기지 않음 - 이 글만의 한계는 구체적으로 한 문장. [rules 주의 문구]
11. 섹션(<h3>)마다 <strong> 한 줄 답은 최대 1개, 숫자 든 사실 문장(판단·권유 금지). 도입·FAQ·정리에는 없음. [rules 한 줄 답]
12. '정리' 섹션 150~300자, 본문 숫자 다시 나열·'첫째·둘째' 목록 없음, '그래서 무엇이 달라지나'. [rules 정리]
13. FAQ는 설계도에 있을 때만, 본문 용어 뜻을 다시 묻지 않음, 답은 자료 안에서. [rules 자주 묻는 질문]
14. 일반론 문장(주제 이름만 바꾸면 다른 글에도 들어갈 문장) 없음 - 문단마다 이 주제 자료의 사실 하나 이상. 군더더기('유기적으로 연결', '복합적인 시각이 필요') 없음. [rules 고유성, 809 고침]
15. 한국어만(종목 코드·고유명사 제외), 쉬운 말, 제목·소제목에 과장·낚시어 없음, 'Part 1' 번호 없음. [rules 한국어만·제목·소제목]
16. 그래프·표를 소개하는 문장('아래 표는 ~') 없음. 연도별 숫자 줄글 나열 없음. [rules 시각 자료 안내·연도별]
17. 모순 없음, %와 %p 구분, 단위·기준일 맞음. [L14]
18. 기업 글이면 회사 이야기만(뉴스·전망·목표주가 없음). [DECISIONS 11-20]

## 5. 점검표 B - 과정·글끼리
1. 읽은 파일이 이번에 받은 최신본인가(커밋 시각 확인). [L17]
2. 모든 old가 최신본에 정확히 1번(명령 결과를 보고서에). [L16]
3. new에 새 숫자 없음.
4. cross_check 결과 + 직접 비교: 정리 틀·계좌 문장·소제목 순서가 같은 종류 글(기업 6편: 809·832·854·870·881·887)과 같은 꼴이 아닌가. [L11, PROJECT_STATUS 보류 8편]
5. 여러 곳을 고쳤다면 고친 문장끼리 같은 꼴이 아닌가. [L4]
6. 이미 공개된 글과 같은 계산 자료를 받는 주제가 아닌가. [DECISIONS 11-21]

## 6. 오류를 찾았을 때 (회장과 나눈 기준, 11-25 사용자 확인)
- 작은 기계적 오류(오타·숫자 하나·한 문장): 회장이 바로 고침. 지부장이 찾았으면 고침 초안에 넣으면 됨.
- 내용·판단 오류(사실·빠짐·다른 글과 겹침·구성): 회장이 근거를 붙여 지부장에게 돌려보냄 → 그 부분 점검표를 처음부터 다시 → 다시 보고.
- 어떤 오류든 LESSONS.txt에 '무엇·왜·막은 법' 한 항목. 같은 종류가 2번이면 IMPROVE.txt에 '코드 검사로 막을 것'을 올림(회장이 코드로).
